# Promotion Review Workflow

Promotion moves extracted candidates into durable surfaces only after review.
Extraction output alone is never enough to write memory, wiki, or reminders.

## Candidate States

Candidates move through these states:

- `candidate`: generated by extraction and waiting for review
- `review_needed`: extraction explicitly requires human review before approval
- `approved`: accepted for dry-run export or promotion
- `rejected`: not eligible for promotion
- `deferred`: held for later review
- `corrected`: reviewer supplied edited content while preserving provenance
- `rollback_needed`: previously approved output needs removal or repair

The initial `candidate` or `review_needed` state is part of the immutable
artifact. Current state and revision live in the queue. Every change requires a
reviewer identity and the revision observed during inspection; a stale revision
fails instead of overwriting a newer decision.

## Legal Transitions

| Current state | Allowed next states |
| --- | --- |
| `candidate` | `review_needed`, `approved`, `rejected`, `deferred`, `corrected` |
| `review_needed` | `candidate`, `approved`, `rejected`, `deferred`, `corrected` |
| `deferred` | `candidate`, `review_needed`, `approved`, `rejected`, `corrected` |
| `approved` | `corrected`, `rollback_needed` |
| `corrected` | `rollback_needed` |
| `rejected`, `rollback_needed` | none |

Each successful transition appends a `review_events` row containing the prior
and new state, reviewer, timestamp, notes, optional correction, and resulting
artifact revision. Database triggers reject update or deletion of those events.

## Approval Gates

Human review is required for:

- durable memory or wiki writes
- reminders and task proposals
- relationship facts about people, companies, accounts, or projects
- obligations, deadlines, legal, billing, travel, or admin events
- any candidate with low confidence, conflicting evidence, or inferred facts

Automatic approval may be considered later only for narrow, high-confidence,
low-risk artifacts with complete source locators and repeatable fixture evidence.

## Review Inputs

Reviewers need:

- candidate content
- source thread and message locators
- evidence references
- classification lane
- confidence and matched rules
- extraction version
- proposed target surface

Evidence references should be short and source-linked, not raw body dumps.
Reviewer notes are append-only audit context, limited to one privacy-safe line
of 512 characters. They are deliberately excluded from promotion exports.

## Correction And Rollback

Corrections must preserve the original candidate and record the reviewer-edited
replacement. Rollback records should identify the promoted artifact, original
candidate, source locator, reason, and removal instructions.

Use `mpi --db ./mpi.db queue inspect <artifact-id>` to read the current
revision, then provide both concurrency and identity fields when deciding:

```bash
mpi --db ./mpi.db queue approve <artifact-id> \
  --reviewer operator@example.test --expected-revision 0 \
  --notes "Evidence confirmed"
mpi --db ./mpi.db queue history <artifact-id>
```

Corrections additionally require `--corrected-summary`. A rollback request is
legal only after approval/correction and requires `--notes`; it marks matching
export outbox records `rollback_needed` without deleting their audit history.

Rejected and deferred candidates must not appear in promotion exports.

## Reminder And Task Rule

Reminder or task creation requires an explicit approved flag separate from
general promotion approval. The reviewer must confirm actor, due date, source,
and desired destination before any reminder/task proposal can be exported.
